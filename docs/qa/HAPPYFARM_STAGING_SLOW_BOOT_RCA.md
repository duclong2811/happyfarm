# HappyFarm staging slow-boot root-cause analysis

Date: 2026-10-11  
Target: `https://happyfarm-staging.longfx.trade/`  
Mode: diagnostics first; no deployment, migration, database write, commit, push, reset, stash, or clean

## Verdict

`BOOT_PERFORMANCE_NEEDS_MORE_EVIDENCE`

The source-level blocking dependency is identified, but an authenticated staging browser waterfall and
real stage marks could not be collected in this environment. No timing result is fabricated.

## 1. Actual startup sequence

1. `index.html` parses the HUD and loads `/src/main.ts` as a module.
2. `main.ts` wires the HUD, performs an initial 2D render, and starts `boot()`.
3. `GET /api/session` establishes or resolves the HttpOnly guest session.
4. The stored farm id is read from local storage.
5. For an existing farm, `loadFarm()` waits in this order:
   - `GET /api/farms/:id`
   - `GET /api/farms/:id/orchard/visual` (best-effort, but currently awaited)
   - `GET /api/fishing` and `GET /api/fishing/active` in parallel
   - `GET /api/resource-nodes` and `GET /api/resource-actions/active` in parallel
   - `POST /api/farms/:id/auto/reconcile`
   - `POST /api/farms/:id/production/reconcile`
   - `refreshAccount()` after successful production reconciliation: nine account/catalogue reads in parallel
   - `refreshFarm()`: tiles, crops, trees, constructions, and aquaculture ponds in parallel
   - `refreshAccount()` again: the same nine account/catalogue reads in parallel
6. Only after `loadFarm()` resolves does `enable3D()` create the WebGL renderer and scene.
7. The scene builds procedural terrain, world/collision state, tile/crop/tree presentation, and the first
   render synchronously. The loading status is then changed to the ready message.
8. GLB models are requested lazily through `GLTFLoader.loadAsync()`. Placeholder geometry is available,
   and these model promises are not awaited before the first frame.

For a new farm, `createFarm()` replaces the existing-farm path with `POST /api/farms`, then fishing,
resources, the full farm refresh, and one account refresh. It does not run the existing-farm production
reconciliation path.

## 2. Sequential versus independent work

The five farm lists are already parallel with one another. Fishing and resource reads are also parallel
inside their own functions, and account reads are parallel inside `refreshAccount()`.

The main avoidable serial chain is the surrounding orchestration: orchard visuals, fishing/resources,
Auto reconciliation, Production reconciliation, farm lists, and account state are awaited one stage at a
time. Production reconciliation is particularly significant because its success path calls
`refreshAccount()` internally, followed by the normal `refreshAccount()` later in `loadFarm()`.

Static catalogue reads and reconciliation are not required to construct the initial terrain/farm scene.
That is the minimal-fix area to measure first; no behavior change was made without authenticated timing.

## 3. Diagnostic instrumentation

Added opt-in development instrumentation, enabled only in Vite development mode with `?perf=1`:

`app_started`, `session_resolved`, `farm_loaded`, `world_init_started`, `assets_loaded`,
`first_3d_frame`, and `game_interactive`.

The browser exposes the captured records as `window.__happyFarmBootPerf` and logs API method, path,
status, and duration. Request bodies, headers, cookies, and response data are never recorded.

`assets_loaded` is deliberately defined as blocking renderer setup complete. Imported GLB assets remain
lazy and fallback-backed; their arrivals are not a boot prerequisite.

## 4. Timing evidence

### Public staging probes

Three read-only curl samples per endpoint were collected. These are not authenticated farm-bootstrap
timings:

| Endpoint | Status | Bytes | Observed total seconds |
|---|---:|---:|---:|
| `/` | 200 | 18,427 | 0.578, 0.604, 1.007 |
| `/api/health` | 200 | 34 | 0.571, 1.957, 2.739 |
| `/api/session` | 200 | 103 | 1.577, 2.560, 2.774 |
| `/api/shop` | 401 | 100 | 0.584, 0.716, 1.120 |

The session and health samples show network/edge variance, but they do not identify the farm-load or D1
stage without the authenticated browser session and farm id.

### Local build evidence

The production web bundle generated by the validation build is 1,235,242 bytes uncompressed for the
main JavaScript chunk. Vite reports 326.21 kB gzip and a chunk-size warning. This may affect initial
JavaScript evaluation on slower devices, but the observed HUD appears before the 3D world and the
renderer is created only after the API bootstrap, so it is not sufficient evidence for the reported
green-screen wait.

No before/after startup timing is reported: no behavior fix was applied and no authenticated staging
browser run was available.

## 5. Three.js/rendering findings

- `new WebGLRenderer(...)` is synchronous and occurs only in `enable3D()` after farm bootstrap.
- `buildFarmSceneInput()` and `buildFarmWorld()` are synchronous pure projections.
- Terrain creation samples a 56-ring by 128-sector island mesh and computes vertex normals.
- Collision/world-cell and dynamic scene layers are rebuilt before `setState()` draws.
- The first completed `renderer.render(scene, camera)` is now marked by the diagnostic callback.
- Environment, building, crop, and character GLB loads are lazy; the character and scenery have fallback
  primitives and the loader promises are not awaited by boot.

The code therefore supports a possible synchronous-render cost, but it does not support blaming external
model or texture downloads for the initial blank/green wait.

## 6. Error handling findings

- A failed session sets an error status and shows the existing boot retry control; there is no retry loop.
- A stored farm returning `RESOURCE_NOT_FOUND` or `NOT_AUTHORIZED` is discarded once and the page tries
  the create-farm path; it does not retry the stale id forever.
- Other farm-bootstrap failures reach the error status through `run()`, but the same retry control is not
  shown for those failures.
- A WebGL creation failure reports `scene.noWebgl`, but the current hidden 3D control does not provide a
  visible renderer retry path. This should be covered by a browser test before any UI fix.
- `ApiClient` does not automatically retry 401 responses.

No arbitrary timeout was added.

## 7. Root-cause classification

`G. Multiple bottlenecks`, with the primary code-confirmed blocker in `C. Auth/Farm initialization`:

1. The farm bootstrap is a long serial dependency chain.
2. Production reconciliation is awaited before renderer creation despite the source comment saying it
   must not block game loading.
3. A successful Production reconciliation can add a full account refresh, then boot performs another one.
4. Public staging latency is variable, so each serial edge request can compound the delay.

The available evidence does not establish whether Worker/D1 latency, the synchronous scene build, or the
client bundle contributes the largest wall-clock share for the affected authenticated player.

## 10. Exact browser tests still needed

1. Run an authorized authenticated staging browser session with the diagnostic build and collect
   `window.__happyFarmBootPerf` plus the DevTools Network waterfall.
2. Record each farm-bootstrap request’s start/end time, status, response size, and whether it is repeated.
3. Compare `farm_loaded -> world_init_started`, `world_init_started -> first_3d_frame`, and
   `first_3d_frame -> game_interactive`.
4. Test a returning farm with Production Rate data and a farm with no active production assignment.
5. Test a session failure, a farm 401/404, a failed farm read, and a WebGL initialization failure; each
   must produce a usable error/retry state without an infinite loading screen.
6. On a slower device, compare normal quality with `?quality=low` to isolate synchronous render cost.
7. If an authenticated account is authorized, verify Farm, Warehouse, and existing player state without
   mutating economy during the performance run.

No production change was made.
